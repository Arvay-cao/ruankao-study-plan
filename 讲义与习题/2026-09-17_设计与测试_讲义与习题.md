# 第一部分 讲义

## 1. 软件设计总览

### 1.1 软件设计在生命周期中的位置

需求分析（产出：需求规格说明书 SRS）→ **软件设计** → 编码 → 测试 → 维护。

软件设计又分为两个阶段：

| 阶段 | 别名 | 核心任务 | 主要产出 |
| --- | --- | --- | --- |
| **概要设计** | 结构设计 | 把需求转化为软件的**体系结构**：划分模块、确定每个模块的功能、确定模块间的调用关系和接口、设计全局数据结构与数据库 | 结构图（SC）、HIPO 图、概要设计说明书 |
| **详细设计** | 过程设计 | 为每个模块确定**内部算法和数据结构**，用图形/语言工具给出过程性描述，作为编码的依据 | 程序流程图、N-S 图、PAD 图、伪代码（PDL）、详细设计说明书 |

注意：详细设计**不是编码**，它是"还没写代码的编码蓝图"，其结果可以用任何语言实现。

### 1.2 结构化设计方法（SD）

结构化设计以需求阶段的数据流图（DFD）为输入，将信息流分为两类，映射为不同的软件结构：

- **变换流**：信息沿输入通路进入系统，同时由外部形式变换为内部形式，进入变换中心加工后，再沿输出通路变换为外部形式离开系统（输入 → 变换 → 输出）。
- **事务流**：信息到达一个"事务中心"，根据事务的取值/类型从若干条动作路径中选出一条执行。

对应两种设计策略：**变换分析**与**事务分析**。

### 1.3 设计原则与启发式规则

基本原则：

- **模块化**：把程序划分成独立命名且可独立访问的模块，每个模块完成一个子功能。
- **抽象**：自顶向下逐步细化，先关心"做什么"再关心"怎么做"。
- **信息隐蔽（Parnas）**：模块内包含的信息（过程和数据）对于不需要这些信息的模块不可访问。
- **模块独立性**：由**内聚**和**耦合**两个定性标准衡量（本日核心，见第 2 节）。

启发式规则（偶考选择题）：

- 改进软件结构，提高模块独立性（高内聚、低耦合）。
- 模块规模适中：过小导致接口开销大，过大不易理解。
- **深度、宽度、扇出、扇入**适当：
  - 扇出（fan-out）：一个模块直接调用的下级模块数目，**不宜过大**（经验值一般不超过 7）。
  - 扇入（fan-in）：直接调用该模块的上级模块数目，**越大越好**（说明公共利用率高）。
  - 好的结构通常是**顶层高扇出，中层扇出较小，底层模块高扇入**。
- 模块的作用域（受其判定影响的所有模块）应落在控制域（其直接/间接调用的模块）之内。
- 降低模块接口的复杂度和冗余度，接口信息要简单、一致。
- 设计单入口、单出口的模块，避免"病态连接"。
- 模块功能应可以预测（同样的输入产生同样的输出）。

### 1.4 详细设计工具（识别型考点）

| 工具 | 特点 |
| --- | --- |
| 程序流程图 | 最古老、使用最广，但对结构化设计的支持不充分（允许随意跳转） |
| N-S 图（盒图） | 确实消除了 goto 带来的混乱，**强制**设计者使用结构化构造（顺序、选择、循环） |
| PAD 图（问题分析图） | 树形结构，支持**自顶向下逐步求精**，结构清晰 |
| 判定表 | 适合表示复杂条件组合与动作的对应关系 |
| PDL（伪代码/过程设计语言） | 用自然语言+结构化语法的混合描述，便于翻译为代码 |

## 2. 模块独立性：内聚与耦合 ★★★

模块独立性的两个定性度量标准：

- **耦合（Coupling）**：衡量**模块之间**相互联系的紧密程度。耦合越**低**越好。
- **内聚（Cohesion）**：衡量**模块内部**各元素彼此结合的紧密程度。内聚越**高**越好。

设计目标口诀：**高内聚、低耦合**。

### 2.1 耦合（从低到高）

| 耦合类型 | 定义/特征 | 典型场景 |
| --- | --- | --- |
| ① 无直接耦合 | 两个模块之间没有直接关系，不传递任何信息（属于不同控制层次/无调用关系） | 互不相干的两个模块 |
| ② 数据耦合 | 模块间通过参数传递**简单的数据值**（整数、实数等） | `calc(a, b)` 传入两个成绩 |
| ③ 标记耦合（特征耦合） | 模块间传递的参数是**数据结构**（记录、数组、结构体等）的一部分或全部 | 传递整张"成绩单"记录 |
| ④ 控制耦合 | 模块间传递的是**控制信息**（开关、标志、状态），一个模块明显控制另一模块的执行逻辑 | 传"操作类型"参数决定对方执行哪段代码 |
| ⑤ 公共耦合 | 一组模块**共享公共数据环境**（全局变量、公共数据区、公共文件） | 多个模块都读写同一个全局数组 |
| ⑥ 内容耦合 | 一个模块**直接访问**另一个模块的内部数据或程序代码；一个模块通过非正常入口转入另一个模块内部；一个模块有多个入口 | 模块 A 直接改写模块 B 的局部变量 |

**记忆链条（从低到高）**：无直接 → 数据 → 标记 → 控制 → 公共 → 内容。

**判断要点**：
- 传"值"（简单变量）→ 数据耦合；传"结构"（记录/数组）→ 标记耦合；传"指挥信号"（开关/标志）→ 控制耦合。
- "共享全局数据" → 公共耦合；"钻进别人身体内部" → 内容耦合（最差）。
- 设计中**追求数据耦合**，尽量避免控制耦合和公共耦合，**绝对禁止**内容耦合。

### 2.2 内聚（从低到高）

| 内聚类型 | 定义/特征 | 典型场景 |
| --- | --- | --- |
| ① 偶然内聚 | 模块内各部分之间**没有实质性联系**，只是为省事把几段代码凑在一起 | 把多处重复出现的语句随意抽成一个模块 |
| ② 逻辑内聚 | 模块完成**逻辑上相关的一组任务**，调用时由**参数/开关选择**执行其中某一个 | 一个模块既能求最大值又能求最小值，由开关决定 |
| ③ 时间内聚 | 模块内各任务**在同一时间段内执行**（与时间相关，与功能无关） | 初始化模块（分配内存、打开文件、清零变量一起做） |
| ④ 过程内聚 | 模块内各处理元素按**特定的执行顺序**组织（来自同一张流程图的一段流程），前后无数据传递关系 | 按"先查询、再计算、后打印"的顺序组织的一段流程 |
| ⑤ 通信内聚 | 模块内各处理元素**使用同一输入数据或产生同一输出数据** | 对同一个成绩数组分别排序、求平均、统计不及格人数 |
| ⑥ 顺序内聚 | 模块内一个元素的**输出是另一个元素的输入**（流水作业），但整体不一定构成单一功能 | "读入数据并计算"：读入的结果作为计算的输入 |
| ⑦ 功能内聚 | 模块内**所有元素共同完成一个单一、完整的功能**（不可再分） | "求平方根""计算平均分"模块 |

**记忆口诀（从低到高）**：**偶、逻、时、过、通、顺、功**。
谐音助记："哦（偶），罗（逻）师（时）父（过）通（通）顺（顺）功（功）"——越往后越好。

**判断流程（做题套路）**：
1. 先看模块内各部分是否共同完成**单一功能** → 是 = 功能内聚（最高）。
2. 否则看是否存在**输出→输入的流水** → 顺序内聚。
3. 是否**用同一数据/产生同一输出** → 通信内聚。
4. 是否只是**执行顺序**凑一起 → 过程内聚。
5. 是否只是**同一时间**执行（初始化/结束处理）→ 时间内聚。
6. 是否**参数选择多个功能之一** → 逻辑内聚。
7. 完全无联系 → 偶然内聚（最低）。

### 2.3 真题常见考法

- 直接问"耦合/内聚程度由低到高的顺序"（排序题）。
- 给一个模块的场景描述，问属于哪种内聚/耦合（场景题）——**场景题占多数**，重点背典型场景。
- 问"耦合程度最低/最高的分别是什么"（数据耦合最好；内容耦合最差）。
- 综合：提高模块独立性的手段 = 提高内聚 + 降低耦合（分解、信息隐蔽）。

## 3. 软件测试基础

### 3.1 测试的目的（Grenford J. Myers 的经典观点）

1. **测试是为了发现错误而执行程序的过程**；
2. 一个**好的测试用例**是指很可能找到迄今为止尚未发现的错误的用例；
3. 一个**成功的测试**是发现了至今尚未发现的错误的测试。

衍生要点（高频）：
- 测试只能证明错误**存在**，不能证明错误**不存在**（Dijkstra）——即使测试通过，也不能断定程序没有错误。
- **测试用例 = 输入数据 +（与之对应的）预期输出**，缺一不可。

### 3.2 测试原则

- **尽早并不断地进行测试**（测试应贯穿整个生命周期，而非编码之后才做）。
- 程序员应**避免测试自己编写的程序**（心理与习惯盲区；单元测试通常例外，可由开发者先自测）。
- 测试用例应包括**输入和预期输出**。
- 测试用例的设计应包括**合理输入和不合理输入**（无效等价类）。
- 注意**错误群集现象**（缺陷集群/80-20 现象）：发现错误越多的模块，残留错误也可能越多。
- **穷举测试是不可能的**，必须选择典型、高效用例。
- 妥善保存测试计划、用例、出错统计和最终分析报告，为回归测试和后续维护提供依据。

### 3.3 测试与调试的区别（经典对比）

| 对比项 | 测试 | 调试 |
| --- | --- | --- |
| 目的 | **发现**程序中的错误 | **定位并改正**错误 |
| 依据 | 需求规格说明书、设计文档（从"程序应该怎样"出发） | 程序内部逻辑（从"程序实际怎样"出发） |
| 执行者 | 专职测试人员/第三方（单元测试可由开发者做） | 通常由**开发人员**完成 |
| 方法/过程 | 有计划、可由工具或人工进行 | 依赖经验，常用推理、断点、打印等手段 |

### 3.4 静态测试与动态测试

- **静态测试**：不实际运行程序，人工或工具检查代码/文档。三种典型形式：
  - **桌前检查（Desk Checking）**：程序员自己复查代码；
  - **代码走查（Walkthrough）**：走查小组人工"模拟执行"，以开会形式进行；
  - **代码审查（Inspection）**：评审小组依据"常见错误检查单"逐条检查，较走查更正式。
- **动态测试**：实际运行程序，输入测试用例并检查输出（白盒、黑盒均属动态测试）。

## 4. 白盒测试：逻辑覆盖与基本路径测试 ★★★

白盒测试又称**结构测试**、透明盒测试：依据程序**内部逻辑结构**设计测试用例，检查程序的控制流和数据流。

### 4.1 六种逻辑覆盖标准

设判定 `D1 = (A>1) AND (B==0)`、`D2 = (A==2) OR (X>1)`，讲解经典程序：

```c
if (A > 1 && B == 0)  X = X / A;   /* 判定 D1，含条件 c1、c2 */
if (A == 2 || X > 1)  X = X + 1;   /* 判定 D2，含条件 c3、c4 */
```

| 覆盖标准 | 要求 | 强度说明 |
| --- | --- | --- |
| ① 语句覆盖 | 每条**可执行语句**至少被执行一次 | **最弱**。上例只需 1 个用例：A=2, B=0, X=3（两个赋值语句都执行） |
| ② 判定覆盖（分支覆盖） | 每个判定的**取真分支和取假分支**都至少经历一次 | 包含语句覆盖（单入口单出口程序）。上例需 2 个用例 |
| ③ 条件覆盖 | 每个判定中**每个条件**的所有可能取值（真/假）都至少出现一次 | **不一定**覆盖判定的所有分支。上例用 (A=2,B=1,X=1) 与 (A=1,B=0,X=3)：c1~c4 各取过真和假，但 D1 始终为假 |
| ④ 判定-条件覆盖 | **同时**满足判定覆盖和条件覆盖 | 每个分支都走到，且每个条件的真假都出现过。上例 (2,0,4) 与 (1,1,1) 两个用例即可 |
| ⑤ 条件组合覆盖 | 每个判定中**条件取值的所有可能组合**都至少出现一次 | 包含判定-条件覆盖。上例 2 个条件 → 每个判定 4 种组合，共 8 种组合，可用 4 个用例覆盖 |
| ⑥ 路径覆盖 | 程序中**每条可能的执行路径**都至少执行一次 | 覆盖了全部分支/语句。上例有 4 条路径，需 4 个用例；**与条件组合覆盖互不包含** |

**强弱关系总结（必背）**：

- 语句 ⊆ 判定 ⊆ 判定-条件 ⊆ 条件组合（一条递增链，语句最弱）。
- 条件覆盖与判定覆盖**互不包含**（条件覆盖可能漏分支，判定覆盖可能漏条件取值）。
- 路径覆盖 ⊇ 判定覆盖 ⊇ 语句覆盖；但路径覆盖与条件组合覆盖**互不包含**（路径走全了，某条件可能只取过一个值；条件组合全了，可能仍有路径没走过）。
- 循环次数多时路径数量爆炸，路径覆盖难以穷举。

### 4.2 基本路径测试（白盒的代表性系统方法）

步骤（真题考过步骤排序）：
1. 根据代码画出**控制流图**；
2. 计算控制流图的**环形复杂度 V(G)**；
3. 确定 V(G) 条**线性独立路径**（"独立路径"= 至少引入一条新边/未曾走过的边的路径）；
4. 为每条独立路径**设计测试用例**并执行，即可实现对程序基本路径集的覆盖。

### 4.3 其他白盒技术（了解）

- 循环测试（简单循环、嵌套循环、串接循环的测试策略）；
- 数据流测试（按变量的定义-使用链设计用例）；
- 程序插装（在代码中插入探针统计信息）。

## 5. McCabe 环形复杂度 ★★★

环形复杂度（Cyclomatic Complexity）度量程序**逻辑结构的复杂程度**，等于程序中**线性独立路径的条数**。

### 5.1 三个等价计算公式

设控制流图有 E 条边（edge）、N 个节点（node）、D 个判定节点（predicate node，出度 ≥ 2 的节点）：

| 公式 | 表达式 | 说明 |
| --- | --- | --- |
| 边-节点公式 | **V(G) = E − N + 2** | 最常用 |
| 判定节点公式 | **V(G) = D + 1** | 数 if/while/for/case 分支判定个数 |
| 区域数公式 | **V(G) = 平面区域数（含图外无限区域）** | 数"圈"，别忘了图外部那个区域 |

### 5.2 例题精讲

**例 1（顺序双分支）**

```c
read(a, b, c);
if (a > 0) {
    if (b > 0) print("X");
    else       print("Y");
} else print("Z");
print("END");
```

- 节点：①read → ②if(a>0) → ③if(b>0) → ④print X → ⑤print Y → ⑥print Z → ⑦print END，共 **N = 7**。
- 边：①→②，②→③（真），②→⑥（假），③→④（真），③→⑤（假），④→⑦，⑤→⑦，⑥→⑦，共 **E = 8**。
- **V(G) = 8 − 7 + 2 = 3**。
- 验证：判定节点 D = 2（两个 if）→ V(G) = 2 + 1 = 3 ✓；区域数 = 3 ✓。
- 独立路径（3 条）：①→②③④⑦；①→②③⑤⑦；①→②⑥⑦。

**例 2（含循环）**

```c
i = 1; sum = 0;
while (i <= n) {
    sum = sum + i;
    i = i + 1;
}
print(sum);
```

- 节点：①初始化 → ②while(i<=n) → ③循环体 → ④print，共 N = 4。
- 边：①→②，②→③（真），③→②（**回边**），②→④（假），共 E = 4。
- **V(G) = 4 − 4 + 2 = 2**；判定节点 D = 1 → V = 2 ✓。
- 独立路径：①②④（循环 0 次）；①②③②④（循环 1 次）。

### 5.3 考点提醒

- V(G) 的含义是**独立路径条数**——这也是"为实现基本路径覆盖，至少需要多少个测试用例"的答案。
- 画控制流图时：顺序语句可合并为一个节点；判定节点画菱形；复合条件（如 `A && B`）**不拆开**时算 1 个判定节点（拆开算 2 个，结果一致——每拆一个条件，边、节点各增加，V(G) 不变）。
- 三种公式结果必须一致，考场上用第二种（数判定）最快，用第一种验算。

## 6. 黑盒测试 ★★★

黑盒测试又称**功能测试**：把程序看成"黑盒子"，完全不考虑内部结构，只依据**需求规格说明书**检查程序功能是否符合要求。常用方法：等价类划分、边界值分析、错误推测、因果图。

### 6.1 等价类划分法

思想：把输入域划分为若干**等价类**，从每类中取一个代表值作为测试数据（用少量代表性数据代替大量同类数据）。

- **有效等价类**：合理的、有意义的输入，检验程序是否实现了规定的功能。
- **无效等价类**：不合理的、无意义的输入，检验程序的容错能力。

划分原则（教材列表）：

| 输入条件类型 | 划分方法 |
| --- | --- |
| 规定了取值范围（如 1~100） | 1 个有效（范围内），2 个无效（< 下界、> 上界） |
| 规定了输入个数（如 1~5 个） | 1 个有效，2 个无效（个数太少、个数太多） |
| 布尔量（是/否） | 1 个有效，1 个无效 |
| 一组值（n 个），程序对每个值分别处理 | n 个有效 + 若干无效 |
| 规定了必须成立的规则 | 1 个有效（符合），若干无效（不同角度违反） |

**用例设计原则（必背）**：
- 设计一个用例，使它**尽可能多地覆盖尚未覆盖的有效等价类**；
- 设计一个用例，使它**只覆盖一个**尚未覆盖的无效等价类（一次只测一种错误，避免屏蔽）。

**经典例子**：输入为学生成绩（0~100 的整数）：
- 有效等价类：0 ≤ 成绩 ≤ 100 的整数（1 个）；
- 无效等价类：①非整数（小数、字母等）；②整数但 < 0；③整数但 > 100（3 个）。

### 6.2 边界值分析法

大量错误发生在输入/输出范围的**边界**而非内部。选取原则：选取**等于、略小于、略大于边界**的值作为测试数据。

- 对范围 [1, 100]：取 1、100（边界上），0、101（刚刚越界），必要时加 2、99（边界内侧邻值）。
- 若输入是"长度为 1~6 的字符串"：除长度边界外，还可考虑空串、超长串。
- 边界值分析常作为等价类划分的**补充**，二者往往联合使用。

### 6.3 错误推测法

依靠测试人员的**经验和直觉**，推测程序中可能存在的错误和易错情形，有针对性地设计用例。

典型易错点：输入为空/0/负数、除零、数组越界、重复记录、并发操作、边界值本身等。

### 6.4 因果图法

等价类和边界值只孤立考虑单个输入，**不适合检查输入条件的组合**。因果图法分析输入（原因）与输出（结果）之间的逻辑关系，最终生成**判定表**并据此设计用例。

因果图的基本符号（原因→结果）：

| 符号 | 名称 | 含义 |
| --- | --- | --- |
| ≈（恒等） | identity | 原因出现则结果出现 |
| ~（非） | NOT | 原因出现则结果不出现 |
| ∨（或） | OR | 几个原因中有一个出现，结果就出现 |
| ∧（与） | AND | 几个原因同时出现，结果才出现 |

约束符号（对原因/结果施加的约束）：

| 符号 | 名称 | 含义 |
| --- | --- | --- |
| **E** | 互斥（Exclusive） | a、b 中**至多一个**可能为 1 |
| **I** | 包含（Inclusive） | a、b、c 中**至少一个**是 1 |
| **O** | 唯一（Only one） | a、b 中**有且仅有一个**是 1 |
| **R** | 要求（Requires） | a 为 1 时，b **必须**为 1 |
| **M** | 屏蔽（Masked） | a 为 1 时，b 强制为 0 |

判定表四要素（因果图的落地形式）：条件桩、动作桩、条件项、动作项；每一列规则对应一个测试用例。

## 7. 测试阶段与实施

### 7.1 与 V 模型的对应关系

| 开发阶段 | 对应测试阶段 |
| --- | --- |
| 需求分析 | 验收测试 |
| 概要设计 | 系统测试 |
| 详细设计 | 集成测试 |
| 编码 | 单元测试 |

### 7.2 单元测试（模块测试）

- 依据：**详细设计说明书**。主要采用**白盒测试为主、黑盒为辅**。
- 主要内容五项（教材列举）：
  1. 模块**接口**（参数个数/类型/顺序、全局量、I/O 文件）；
  2. **局部数据结构**；
  3. **独立路径**（保证模块内所有语句至少执行一次）；
  4. **出错处理通路**；
  5. **边界条件**（最容易出错的地方）。
- 由于模块不是独立程序，测试时需要配套模块：
  - **驱动模块（driver）**：模拟调用被测模块的**上级**模块（自底向上集成时需要）；
  - **桩模块（stub）**：模拟被测模块所**调用的下级**模块（自顶向下集成时需要）。
  - 记忆："驱动在上推着跑，桩在下面垫着撑"——驱动是"上级替身"，桩是"下级替身"。

### 7.3 集成测试（组装测试）

- 依据：概要设计说明书。把模块装配成系统，测试接口与装配后的整体功能。
- **非增量式（一次性/大爆炸）集成**：全部模块一次性组装，错误难以定位，不推荐。
- **增量式集成**（重点）：

| 策略 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 自顶向下 | 从主控模块开始，沿控制层次向下逐步接入模块 | 较早验证**主要控制和判定点**；较早形成程序雏形 | 需要大量**桩模块**；底层模块错误暴露晚 |
| 自底向上 | 从最底层模块开始向上组装 | 底层模块较早得到验证；**驱动模块比桩模块易写** | 主控模块的错误最后才能发现；程序整体雏形出现晚 |
| 三明治（混合） | 上层用自顶向下、下层用自底向上 | 兼具两者优点 | 需同时编写桩和驱动，工作量较大 |

### 7.4 确认测试（有效性测试）

- 依据：**需求规格说明书**，验证软件的功能和性能是否与用户需求一致。
- 内容：有效性测试 + **软件配置审查**（文档与程序的一致性、完整性）。
- 用户参与形式：
  - **α 测试**：用户在**开发环境**（开发场所/开发者指导下）进行的测试；
  - **β 测试**：多个用户在**实际使用环境**下进行的测试，开发者通常**不在现场**，用户独立记录问题反馈。
  - 记忆：α 在"家里"（开发方处），β 在"外面"（真实环境）。

### 7.5 系统测试

把软件与整个计算机系统（硬件、外设、网络、其他系统软件等）结合起来测试。常见类型：功能测试、**性能测试**、压力测试/强度测试、负载测试、恢复测试、安全测试、兼容性测试、安装测试等。区分：
- 性能测试：验证系统在正常/峰值负载下的响应时间、吞吐量等指标是否满足要求；
- 压力（强度）测试：施加超常负载，看系统在极限情况下的表现和恢复能力。

### 7.6 回归测试

软件修改（改正错误、增加功能、环境变更）之后，为验证**修改没有引入新的错误**而重新进行的测试。回归测试应尽量利用原来已通过测试的用例集，是维护阶段最常用的测试手段。

## 8. 软件维护 ★★

软件维护是生命周期的最后一个阶段，发生在**交付使用之后**。可维护性通常包括：易理解性、易测试性、易修改性。

### 8.1 四种维护类型（按性质划分）

| 类型 | 触发原因 | 典型场景 | 典型占比 |
| --- | --- | --- | --- |
| **纠正性维护** | 交付后**发现潜在错误**，改正错误 | 用户使用中发现闰年日期计算出错，开发方修复 | 约 20% |
| **适应性维护** | **运行环境变化**（硬件、操作系统、数据环境、法规政策等），使软件适应新环境 | 操作系统升级换代后修改代码使其继续运行；税法修改后调整计算规则 | 约 25% |
| **完善性维护** | 用户提出**增加功能、改善性能**的要求 | 用户要求增加"按部门导出报表"功能；优化查询速度 | **约 50%（最大）** |
| **预防性维护** | 为**将来的可维护性、可靠性**奠定基础，主动修改 | 重构老旧代码、更新文档、提高可移植性 | 约 5% |

**占比口诀**：完善 > 适应 > 纠正 > 预防（"完适纠预"，完善性维护约占一半）。

**场景判断技巧**：题目出现"环境/平台/系统升级、外部规则变化"→ 适应性；"用户要求增加新功能、优化体验"→ 完善性；"发现了错误（bug）"→ 纠正性；"为了将来、预防性重构"→ 预防性。

### 8.2 维护的副作用

修改软件时可能引入新问题（回归错误），包括三类：
1. **修改代码的副作用**；
2. **修改数据的副作用**（数据结构、文件内容变动）；
3. **修改文档的副作用**（文档与程序不一致）。

因此维护后必须进行**回归测试**，并保持文档同步更新。

## 9. 当天产出：测试方法对照表

### 9.1 白盒 vs 黑盒总览

| 方法 | 类别 | 核心思想 | 适用/关键词 | 考点标志词 |
| --- | --- | --- | --- | --- |
| 语句覆盖 | 白盒 | 每条语句至少执行一次 | 最基本、最弱 | "每条语句" |
| 判定覆盖（分支覆盖） | 白盒 | 每个判定真假分支各走一次 | 含语句覆盖 | "真假分支" |
| 条件覆盖 | 白盒 | 每个条件的真假各出现一次 | 不保证分支全覆盖 | "每个条件所有取值" |
| 判定-条件覆盖 | 白盒 | 判定覆盖 + 条件覆盖 | 双重满足 | "同时满足判定和条件" |
| 条件组合覆盖 | 白盒 | 每个判定内条件取值的所有组合 | 强度高、用例多 | "所有组合" |
| 路径覆盖 | 白盒 | 所有可执行路径各走一次 | 与条件组合互不包含 | "每条路径" |
| 基本路径测试 | 白盒 | 流图 → V(G) → 独立路径 → 用例 | 与 McCabe 结合出题 | "独立路径""基本路径集" |
| 等价类划分 | 黑盒 | 输入域分类，取代表值 | 无效类一次只测一个 | "等价类" |
| 边界值分析 | 黑盒 | 取边界及邻近值 | 最易出错的位置 | "边界、刚刚越界" |
| 错误推测 | 黑盒 | 凭经验和直觉猜错误 | 灵活、无固定步骤 | "经验、直觉、易错" |
| 因果图 / 判定表 | 黑盒 | 输入条件组合与输出的逻辑关系 | 组合爆炸时系统化处理 | "条件组合、原因结果" |

| 阶段 | 依据 | 主要手段 | 配套/替身 |

| 回归测试 | 变更单 | 重用旧用例 | 贯穿修改后全过程 |

| 类型 | 一句话触发词 | 占比 |

# 第四部分 答案与详细解析

## 一、模块独立性（1—8 题）

**1. 答案：A**
【考点：耦合排序】耦合由低到高：无直接耦合 → 数据耦合（传简单值）→ 标记耦合（传数据结构）→ 控制耦合（传控制信息）→ 公共耦合（共享公共数据）→ 内容耦合（直接访问内部）。B 错在"数据"与"无直接"位置颠倒；C 错在"控制"与"标记"顺序颠倒（标记耦合低于控制耦合）；D 错在"标记"提到"数据"之前。

**2. 答案：B**
【考点：标记耦合】传递的是数据结构（记录/结构体/数组）的一部分或全部，属于标记耦合。若只传简单数据值（如一个整数分数）才是数据耦合；本题传的是整张"成绩单记录"，故为标记耦合。

**3. 答案：C**
【考点：控制耦合】传递开关、标志等"控制信息"并影响被调模块的执行逻辑，是控制耦合的定义。控制耦合的模块之间关系不平等，是应尽量避免的耦合形式。

**4. 答案：B**
【考点：内容耦合】直接访问另一模块内部数据、非正常入口转入、一个模块有多重入口，都属于内容耦合——耦合程度最高、独立性最差，设计中绝对禁止。公共耦合是"共享全局数据区"，二者要区分：内容耦合是"钻进对方内部"，公共耦合是"共用同一块公共区域"。

**5. 答案：A**
【考点：内聚排序】口诀"偶、逻、时、过、通、顺、功"（偶然 → 逻辑 → 时间 → 过程 → 通信 → 顺序 → 功能）。B 把"时间"提到"逻辑"之前；C 把"逻辑"放到首位且通信/顺序顺序颠倒；D 把"通信"提到"过程"之前。

**6. 答案：B**
【考点：逻辑内聚】模块完成逻辑上相关（相似）的一组任务，执行哪一个由传入的参数/开关决定——典型的逻辑内聚。注意与偶然内聚区分：偶然内聚是各部分毫无联系地凑在一起，**没有**"参数选择"这一特征；本题明确"通过入口参数选择执行其中之一"，且三个功能在"功能调用"这个逻辑上相似，故为逻辑内聚。

**7. 答案：C**
【考点：时间内聚】初始化模块中各操作仅因"程序启动时要在同一时间段内完成"而聚在一起，与功能无关，是时间内聚的教科书级例子。若这些操作毫无任何共同点且是随手抽取，才是偶然内聚；本题的归类依据是"时间"，选时间内聚。

**8. 答案：B**
【考点：通信内聚】各处理功能使用**同一输入数据**（同一成绩数组），属于通信内聚（又可称数据内聚）。顺序内聚要求"前一个处理的输出是后一个处理的输入"（流水关系），本题排序、求平均、统计之间没有输出→输入关系，故不是顺序内聚。

## 二、测试基础（9—10 题）

**9. 答案：D**
【考点：Myers 测试目的】Myers 的三个经典观点：测试是发现错误而执行程序的过程；好的测试用例是很可能找到迄今尚未发现错误的用例；成功的测试是发现了至今尚未发现错误的测试。测试**不能证明程序无错**，D 与之相反，故选 D。

**10. 答案：C**
【考点：测试与调试】A、B 为测试与调试的正确区别；D 是单元测试的通行做法（白盒为主黑盒为辅）；C 错误——测试无论多么充分，都只能证明错误的存在，不能证明软件不存在错误（穷举测试不可行），这是测试的固有局限。

## 三、白盒测试与逻辑覆盖（11—16 题）

**11. 答案：A**
【考点：覆盖强度】语句覆盖只保证"每条语句至少执行一次"，对程序逻辑的检验最不充分，是最弱的标准。例如 `if (A && B)` 为假的多种方式它都不区分。

**12. 答案：B**
【考点：判定覆盖】"每个判定的取真分支和取假分支都至少经历一次"即判定覆盖（分支覆盖）。A 语句覆盖只管语句；C 条件覆盖管条件取值；D 条件组合覆盖管组合。

**13. 答案：C**
【考点：条件覆盖】条件覆盖只要求每个**条件**的真假都出现过，不保证判定整体取真、取假分支都被走到（例如 (A=T,B=F) 与 (A=F,B=T) 使 `A&&B` 两次都为假）。这正是"条件覆盖不一定包含判定覆盖"的原因。

**14. 答案：B**
【考点：判定-条件覆盖】同时满足判定覆盖（分支都走）与条件覆盖（条件取值都出现）的即是判定-条件覆盖。

**15. 答案：B**
【考点：覆盖强弱关系】
- A 错：条件覆盖不一定满足判定覆盖（见 13 题解析）；
- B 对：单入口单出口的结构化程序中，每个判定的真假分支都走过，则所有语句必被执行（语句都挂在分支上）；
- C 错：路径覆盖与条件组合覆盖互不包含——路径走全了，某个条件可能始终只取一个值；
- D 错：语句覆盖只保证语句执行，判定的某个分支（其中无语句，或语句已被其他用例执行）可能从未走过。

**16. 答案：A**
【考点：语句覆盖用例数】取 A=2、B=0、X=3：第一个判定 (A>1 && B==0) 为真 → 执行 X=X/A（X=1.5）；第二个判定 (A==2 || X>1) 为真 → 执行 X=X+1。两个赋值语句均被执行，**1 个用例**即可达到语句覆盖。这也是语句覆盖"最弱"的直观体现。

## 四、McCabe 环形复杂度（17—20 题）

**17. 答案：C**
【考点：V(G)=E−N+2】V(G) = 12 − 9 + 2 = 5。计算题必须先数清边数（含循环回边）和节点数（顺序语句可合并成一个节点）。

**18. 答案：B**
【考点：V(G)=D+1】判定节点 D=4（连通图，单程序段），V(G) = 4 + 1 = 5。与 17 题互为验证：两种公式结果一致。

**19. 答案：B**
【考点：V(G) 的含义】环形复杂度 = 程序中**线性独立路径**的条数，也等于覆盖基本路径集所需测试用例数的下限。它与语句条数、节点数没有直接相等关系。

**20. 答案：B**
【考点：代码求 V(G)】控制流图：节点 7 个（①read，②if(a>0)，③if(b>0)，④print X，⑤print Y，⑥print Z，⑦print END），边 8 条（①→②，②→③，②→⑥，③→④，③→⑤，④→⑦，⑤→⑦，⑥→⑦）。V(G) = 8 − 7 + 2 = **3**。用判定节点验证：2 个 if → V = 2 + 1 = 3 ✓。独立路径三条：ab→X→END；ab→Y→END；a 假→Z→END。

## 五、黑盒测试（21—26 题）

**21. 答案：A**
【考点：方法分类】等价类划分、边界值分析、错误推测、因果图是黑盒四大常用方法。B、C 中语句/判定/条件覆盖、基本路径、循环测试均为白盒方法；D 中代码走查属于**静态测试**、路径覆盖属于白盒，均混入非黑盒方法。

**22. 答案：C**
【考点：等价类划分】按规则"0~100 的整数"逐条分析无效输入：①非整型数据（小数、字母、空值等）；②整数但小于 0；③整数但大于 100。共 **3** 个无效等价类（有效等价类 1 个：0~100 之间的整数）。注意：设计用例时每个无效等价类要单独用一个用例覆盖。

**23. 答案：A**
【考点：边界值分析】边界值分析应选取边界上的值（1、100）以及刚刚越界的值（0、101）。B 只有边界没有越界值，还混入了中间值 50；C 只有边界内侧邻值，缺边界值本身；D 的取值远离边界，毫无意义。

**24. 答案：D**
【考点：因果图适用场景】等价类和边界值都只孤立地考察单个输入条件；因果图法专门分析**输入条件的组合**与输出的逻辑关系，并最终生成判定表来设计用例。关键词"组合"→因果图。

**25. 答案：A**
【考点：因果图约束符号】E（互斥）：a、b 至多一个为 1；I（包含）：至少一个为 1；O（唯一）：有且仅有一个为 1；R（要求）：a 为 1 则 b 必须为 1；M（屏蔽）：a 为 1 时 b 强制为 0。区分 E 与 O："至多一个"允许同时为 0，"唯一"不允许同时为 0。

**26. 答案：C**
【考点：错误推测法】凭测试人员的经验和直觉列举程序中可能有的错误和易发生错误的特殊情况，据此设计用例，即错误推测法。它没有固定的步骤和规程，是最灵活的黑盒方法。

## 六、测试阶段与实施（27—31 题）

**27. 答案：B**
【考点：桩模块与驱动模块】自顶向下集成从主控模块开始向下装配，下层被调用模块尚未接入时，用**桩模块**（stub）代替其接受调用、返回模拟结果；自底向上集成时才需要编写**驱动模块**（driver）模拟上级调用。记忆："驱动是上级替身，桩是下级替身；自顶向下缺下级（桩），自底向上缺上级（驱动）"。

**28. 答案：C**
【考点：α/β 测试】α 测试：用户在**开发环境**下进行，通常有开发人员指导；β 测试：多个用户在**实际使用环境**下独立进行，开发人员通常不在现场，由用户记录问题后反馈。A 描述的是 β 测试；B 把两者说反；D 否定了用户参与，均错误。

**29. 答案：B**
【考点：三明治集成】三明治（混合）集成对上层模块采用自顶向下、对下层模块采用自底向上，兼顾"较早验证主要控制"与"较早验证底层通用模块"两个优点，代价是需要同时编写驱动模块和桩模块。

**30. 答案：A**
【考点：确认测试任务】确认测试（有效性测试）以**需求规格说明书**为依据，验证软件功能与性能是否与用户需求一致，并附软件配置审查。B 是集成测试的任务；C 属于静态测试（代码审查/规范检查）；D 是系统测试的任务。

**31. 答案：B**
【考点：回归测试】修改后重新测试以确认**没有引入新错误**，即回归测试，通常大量重用原有测试用例。冒烟测试是对每日构建的基本功能快速验证；强度测试属于系统测试中的负载极限测试。

## 七、软件维护（32—35 题）

**32. 答案：B**
【考点：适应性维护】因**运行环境变化**（操作系统从 Windows 迁移到 Linux）而修改软件，属于适应性维护。判断标志：程序本身没有错、需求也没加，是"外部环境变了"。

**33. 答案：C**
【考点：完善性维护】用户主动提出**增加新功能**（按部门导出报表），属于完善性维护——这也是实际工作中占比最大（约 50%）的维护类型。

**34. 答案：C**
【考点：维护占比】典型占比：完善性约 50% > 适应性约 25% > 纠正性约 20% > 预防性约 5%。口诀"完适纠预"。

**35. 答案：A**
【考点：纠正性维护】交付使用后**发现并改正程序错误**（闰年日期计算错误），属于纠正性维护。注意与适应性维护区分：本题是程序自身的 bug，不是环境变化。
